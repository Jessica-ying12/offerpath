## Q1. Webpack 的构建流程？

**直接回答：**

> 从 entry 开始，递归解析依赖，构建模块依赖图；每个模块根据规则交给 loader 转换；plugin 在生命周期钩子上做扩展；最后生成 chunk，做 tree shaking、压缩、代码分割，输出到 output。核心是 Compiler 和 Compilation，基于 Tapable 的钩子机制。

**追问 1：Webpack 为什么需要依赖图？**

> 它要从入口找到所有用到的模块，处理循环依赖、代码分割、公共依赖提取，最终决定 chunk 怎么拆。

**追问 2：loader 的执行顺序？**

> 从右往左、从下往上执行；比如 `['style-loader', 'css-loader', 'postcss-loader']` 先 postcss，再 css，最后 style。

**陷阱/加分：**

- Webpack 5 内置了持久化缓存。
- 构建流程不是“一次性打包所有文件”，而是按依赖图处理模块。

## Q2. loader 和 plugin 的区别？

**直接回答：**

> loader 是模块转换器，处理单个文件的转换，比如把 JSX 转 JS、SCSS 转 CSS，配置在 `module.rules` 里；plugin 是插件，监听构建生命周期钩子，能做更复杂的事，比如生成 HTML、抽离 CSS、定义环境变量。

**追问 1：loader 能异步吗？**

> 能，用 `this.async()` 返回 callback；也可以用 `promise` 形式。

**追问 2：plugin 怎么工作？**

> 通过 Tapable 注册钩子，在 compile/make/emit 等阶段执行；plugin 可以访问 compiler/compilation。

**陷阱/加分：**

- loader 关注“文件怎么转”，plugin 关注“构建过程怎么做”。
- 不要用 plugin 做单文件转换，也不要用 loader 做全局构建优化。

## Q3. Tree Shaking 的原理？条件是什么？

**直接回答：**

> 基于 ES Module 的静态结构，打包时分析哪些导出被使用，删除未使用的代码。前提是 ESM、生产模式、`sideEffects` 配置正确；CommonJS 运行时加载，通常无法可靠 tree shaking。

**追问 1：`sideEffects: false` 有什么用？**

> 告诉打包工具模块没有副作用，可以安全删除未使用的导入；有 CSS/全局初始化的包要单独标注。

**追问 2：为什么 `import './style.css'` 可能被删？**

> 如果包声明 `sideEffects: false`，工具会认为这个导入没副作用；要配置 `sideEffects: ["*.css"]`。

**陷阱/加分：**

- tree shaking 删除的是未使用的导出，不是所有死代码。
- 动态 import 是代码分割，不是 tree shaking。

## Q4. Webpack 怎么优化构建速度？

**直接回答：**

> 缩小 loader 范围（exclude/include）；开启 filesystem 缓存和 babel 缓存；多线程 thread-loader/esbuild-loader；减少 resolve 范围；生产环境关闭 sourcemap 或改用 cheap；升级 Webpack 版本；减少不必要的 plugin。

**追问 1：缓存怎么配？**

> `cache: { type: 'filesystem' }`；babel-loader 也有 `cacheDirectory`；注意缓存失效条件。

**追问 2：多线程一定快吗？**

> 不一定，启动线程有开销；大项目收益明显，小项目可能更慢。

**陷阱/加分：**

- 先测量再优化，不要盲目加 loader/plugin。
- 开发环境不要做生产级压缩/抽离 CSS。

---

## Q5. Webpack 怎么优化产物体积？

**直接回答：**

> Tree shaking；代码分割（动态 import、splitChunks）；压缩 JS/CSS；图片压缩和合适格式；按需引入组件库；externals 把大依赖放 CDN；分析 bundle 找大模块。

**追问 1：怎么分析包体积？**

> 用 `webpack-bundle-analyzer` 生成可视化报告，找大依赖/重复依赖/未使用代码。

**追问 2：`splitChunks` 怎么拆？**

> 把 node_modules 拆成 vendor、公共代码拆成 common、运行时代码单独抽离；不要拆得太碎，增加请求数。

**陷阱/加分：**

- 长效缓存用 `[contenthash]`，不要用 `[hash]`。
- 图片/字体往往是大头，别只盯 JS。

---

## Q6. HMR 是什么？原理？

**直接回答：**

> 热模块替换，修改代码后只替换变化的模块，不刷新页面，保留页面状态。Webpack 通过 devServer 和 HMR runtime 实现；React 用 react-refresh，Vue 用 vue-loader。

**追问 1：HMR 和热重载的区别？**

> HMR 只替换模块，保留状态；Live Reload/热重载通常刷新页面，状态丢失。

**追问 2：为什么有时 HMR 不生效？**

> 模块没有 accept 处理、状态不可序列化、改了全局/main/原生代码、缓存问题；需要刷新或重启。

**陷阱/加分：**

- HMR 是开发环境能力，生产不会用。
- HMR 失败要有 fallback 刷新。

---

## Q7. Vite 为什么快？

**直接回答：**

> 开发环境利用浏览器原生 ESM，按需编译，不打包整个项目；依赖用 esbuild 预构建，速度快；HMR 基于 ESM，只更新变化的模块。生产构建用 Rollup。

**追问 1：Vite 生产构建也快吗？**

> 生产用 Rollup，构建速度和产物质量取决于项目；开发快不等于生产打包快。

**追问 2：Vite 和 Webpack 怎么选？**

> 新项目优先 Vite（启动快、配置少）；老项目/需要复杂 loader/plugin 生态继续 Webpack；看团队和构建需求。

**陷阱/加分：**

- Vite 开发时不是“不编译”，是按需编译。
- 浏览器原生 ESM 需要现代浏览器。

## Q8. npm 的 `^` 和 `~` 有什么区别？lockfile 有什么用？

**直接回答：**

> `^1.2.3` 允许更新到 1.x.x 的最新版，不跨主版本；`~1.2.3` 只允许 1.2.x，不跨次版本。lockfile 锁定实际安装版本，保证团队/CI 一致；`npm ci` 按 lockfile 精确安装。

**追问 1：`npm install` 和 `npm ci` 的区别？**

> install 可能更新 lockfile/安装范围；ci 严格按 lockfile 安装，适合 CI，要求 lockfile 存在。

**追问 2：怎么升级依赖更安全？**

> 先看 changelog/breaking change，升级后跑测试；主版本升级尤其要谨慎。

**陷阱/加分：**

- `latest`/`*` 不可控，生产避免。
- lockfile 要提交到 Git。

## Q9. `dependencies` 和 `devDependencies` 的区别？

**直接回答：**

> dependencies 是运行时依赖，会被打包/部署；devDependencies 是开发、构建、测试用的工具，不进入生产包。组件库的 React 应该放 peerDependencies，避免重复安装。

**追问 1：构建工具放哪？**

> Webpack/Vite/Babel/ESLint 放 devDependencies；运行时库（React、axios）放 dependencies。

**追问 2：peerDependencies 有什么用？**

> 告诉使用方“我需要你提供这个依赖”，避免组件库和宿主应用装两份 React。

**陷阱/加分：**

- 放错位置可能导致生产缺包或包体积变大。
- `npm i --production` 只装 dependencies。

## Q10. Git merge 和 rebase 的区别？

**直接回答：**

> merge 保留分支历史，生成合并提交；rebase 把当前分支的提交搬到目标分支后面，历史更线性。rebase 会改写提交 hash，不能用于已经推送到共享分支的提交。

**追问 1：什么时候用 rebase？**

> 本地分支同步主分支、整理提交历史；多人共享分支不要 rebase。

**追问 2：冲突怎么解决？**

> 打开冲突文件，保留想要的内容，删除 `<<<<<<<` 标记，`git add` 后继续 merge/rebase。

**陷阱/加分：**

- `git pull --rebase` 可以避免无意义的 merge 提交。
- rebase 后 push 需要 `--force-with-lease`，且只在自己的分支。

---

## Q11. `git reset` 和 `git revert` 的区别？

**直接回答：**

> reset 是移动分支指针，会改写历史，适合本地未推送的提交；revert 是生成一个反向提交，历史保留，适合已推送的提交。`reset --hard` 会丢弃工作区改动，慎用。

**追问 1：`reset --soft`、`--mixed`、`--hard` 的区别？**

> soft 只移动 HEAD，改动留在暂存区；mixed 移动 HEAD，改动留在工作区；hard 移动 HEAD 并丢弃工作区和暂存区改动。

**追问 2：已经 push 的提交怎么撤销？**

> 用 `git revert` 生成反向提交，再 push；不要对共享分支 reset --hard。

**陷阱/加分：**

- reset 前先 `git status`，确认没有未提交工作。
- revert 一个 merge commit 需要指定 mainline。

## Q12. 跨域怎么解决？

**直接回答：**

> 开发环境用 Webpack/Vite 代理；生产环境后端配置 CORS、同域部署或 Nginx 反向代理；JSONP 只支持 GET，已很少用；WebSocket 不受同源限制。

**追问 1：CORS 预检是什么？**

> 带自定义头/非简单方法的请求，浏览器先发 `OPTIONS`，服务端返回允许的 origin/method/header，浏览器再发真实请求。

**追问 2：带 cookie 的跨域要注意什么？**

> 前端 `credentials: 'include'`，服务端 `Access-Control-Allow-Credentials: true`，且 `Allow-Origin` 不能是 `*`。

**陷阱/加分：**

- CORS 是浏览器行为，不是服务器拒绝。
- 代理是开发环境方案，生产要配网关/同域。

## Q13. Axios 怎么封装？

**直接回答：**

> 创建实例配置 baseURL/timeout；请求拦截器加 token；响应拦截器统一处理业务码、401、超时和错误提示；导出 get/post 方法。业务层只关心数据，不重复写错误处理。

**追问 1：401 怎么处理？**

> 清除 token、跳登录；如果有 refresh token，可以做无感刷新，并让并发请求排队等待。

**追问 2：怎么取消请求？**

> 用 `AbortController` 的 signal，或 axios 的 CancelToken（旧）。搜索/切页时取消旧请求，避免竞态。

**陷阱/加分：**

- 响应拦截器直接返回 `res.data` 会让调用方拿不到 header，按团队约定。
- 错误提示不要每个请求都弹，统一处理。

## Q14. ESLint 和 Prettier 的区别？

**直接回答：**

> ESLint 检查代码质量和潜在错误（未使用变量、Hooks 规则、安全规则），Prettier 只管格式（缩进、引号、换行）。两者配合使用，ESLint 负责逻辑，Prettier 负责风格，避免规则冲突。

**追问 1：怎么避免冲突？**

> 用 `eslint-config-prettier` 关闭与 Prettier 冲突的规则；或者用 ESLint 的 stylistic 规则统一。

**追问 2：提交前怎么自动检查？**

> husky + lint-staged，在 pre-commit 对暂存文件跑 eslint --fix 和 prettier。

**陷阱/加分：**

- 不要用 ESLint 做格式化，职责分离。
- 规则要团队统一，不要每个人一套。

---

## Q15. Sourcemap 是什么？生产环境要不要开？

**直接回答：**

> Sourcemap 是压缩代码到源码的映射，方便调试。生产环境可以生成但不要公开部署，上传到监控平台用于还原错误栈；或者用 hidden-source-map，只保留映射文件不引用。

**追问 1：`eval`、`cheap`、`module` 这些前缀什么意思？**

> eval 用 eval 包裹、构建快但映射不精确；cheap 只映射行不映射列；module 映射 loader 处理前的源码。按开发/生产权衡。

**追问 2：sourcemap 会不会泄露源码？**

> 会，如果公开部署，别人能还原源码；生产要限制访问或上传到监控平台。

**陷阱/加分：**

- 生产 sourcemap 要配合错误监控使用。
- 不要提交 sourcemap 到公开 CDN。

## Q16. CI/CD 是什么？前端怎么做？

**直接回答：**

> CI 是持续集成：提交代码后自动安装依赖、lint、测试、构建；CD 是持续部署/交付：构建产物自动发布到测试/生产。前端常用 GitHub Actions/GitLab CI/Jenkins，流程是 checkout → setup node → npm ci → lint → test → build → deploy。

**追问 1：怎么保证构建可复现？**

> 用 lockfile + `npm ci`，固定 Node 版本，环境变量统一管理。

**追问 2：怎么做灰度/回滚？**

> 静态资源带 hash、CDN 灰度、Nginx/网关按比例分流；保留上一版本，出问题快速回滚。

**陷阱/加分：**

- CI 里不要跑 interactive 命令。
- 密钥放 CI secrets，不要写进仓库。

## Q17. 前端性能指标有哪些？怎么优化？

**直接回答：**

> 核心指标：TTFB、FCP、LCP、INP、CLS。优化分加载、运行时、构建：代码分割/tree shaking/压缩/CDN/缓存/图片优化；虚拟列表/防抖节流/减少重渲染/动画用 transform；构建缓存/多线程/包体积分析。

**追问 1：LCP 怎么优化？**

> 首屏大图/大标题优先加载，压缩图片、预加载、CDN、减少阻塞资源、SSR/骨架屏。

**追问 2：INP 是什么？**

> 交互到下一次绘制的延迟，取代 FID；优化长任务、减少 JS 阻塞、拆分任务。

**陷阱/加分：**

- FID 已被 INP 取代，面试提到 INP 会加分。
- 指标要结合真实用户监控（RUM），不只看实验室数据。

## Q18. 前端缓存策略怎么设计？

**直接回答：**

> HTML 用 `no-cache` 每次校验；带 hash 的 JS/CSS 用 `max-age=31536000, immutable`；图片/字体长期缓存；API 按业务设置。强缓存看 `Cache-Control/Expires`，协商缓存看 `ETag/Last-Modified`，命中返回 304。

**追问 1：为什么 HTML 不长期缓存？**

> HTML 里引用的 JS/CSS hash 会变，如果 HTML 被缓存，用户拿不到新资源；所以 HTML 要每次校验。

**追问 2：CDN 缓存怎么刷新？**

> 发布新 hash 文件 + 刷新 HTML/CDN 目录；不要覆盖同名文件，避免缓存不一致。

**陷阱/加分：**

- `immutable` 告诉浏览器不用再校验。
- 缓存要配合版本号和回滚。

## Q19. Monorepo 和 pnpm 是什么？

**直接回答：**

> Monorepo 是把多个包放在一个仓库里统一管理，适合组件库/多端项目；pnpm 用硬链接和内容寻址节省磁盘，依赖更严格，配合 workspace 管理多包。工具还有 Turborepo/Nx。

**追问 1：Monorepo 有什么缺点？**

> 仓库大、构建慢、权限/发布流程复杂；需要缓存、任务编排、版本管理工具。

**追问 2：pnpm 为什么省磁盘？**

> 全局 store + 硬链接，相同版本的包只存一份；node_modules 结构也更严格，避免幽灵依赖。

**陷阱/加分：**

- 小项目不需要 Monorepo，别过度设计。
- 多包发布要处理版本联动/changelog。
