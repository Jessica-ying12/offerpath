## Q1. 数组和链表的区别？

**直接回答：**

> 数组是连续内存，随机访问 O(1)，中间插入/删除 O(n)，缓存友好；链表节点分散，查找 O(n)，已知前驱时插入/删除 O(1)，缓存不友好。随机访问多用数组，频繁头插/删除用链表。

**追问 1：为什么数组随机访问是 O(1)？**

> 元素地址 = 首地址 + 下标 × 元素大小，能直接算出地址。

**追问 2：链表真的插入就比数组快吗？**

> 找到位置本身要 O(n)；只有已经持有前驱节点时，插入才是 O(1)。数组在尾部插入均摊也是 O(1)。

**陷阱/加分：**

- JS 数组不是严格的连续内存，引擎会优化；面试按数据结构语义答。
- 缓存局部性会让数组遍历通常更快。

## Q2. 哈希表的原理？冲突怎么解决？

**直接回答：**

> 哈希表用哈希函数把 key 映射到数组下标，平均查找/插入/删除 O(1)，最坏 O(n)。冲突解决有链地址法（拉链）和开放寻址；负载因子太高要扩容。

**追问 1：为什么最坏是 O(n)？**

> 所有 key 都冲突到同一个桶，退化成链表，查找要遍历 n 个元素。

**追问 2：哈希函数要满足什么？**

> 计算快、分布均匀、相同 key 结果稳定；分布不均会导致冲突多。

**陷阱/加分：**

- JS 的 Map 平均 O(1)，但不保证严格常数。
- 哈希表不保持排序，需要顺序用 Map/树。

## Q3. 二叉搜索树和平衡树有什么区别？

**直接回答：**

> BST 满足左子树 < 根 < 右子树，平均查找 O(log n)，但可能退化成链表，最坏 O(n)。平衡树（AVL/红黑树）通过旋转保持高度平衡，查找/插入/删除稳定 O(log n)。

**追问 1：红黑树和 AVL 怎么选？**

> AVL 更严格平衡，查找快、旋转多；红黑树近似平衡，插入/删除旋转少，工程上更常用（Java TreeMap、C++ map）。

**追问 2：BST 的中序遍历有什么特点？**

> 得到有序序列；验证 BST、找第 k 小都用中序。

**陷阱/加分：**

- BST 的“左<根<右”是对整棵子树，不只是直接子节点。
- 平衡树解决的是退化问题。

## Q4. 堆是什么？用在哪里？

**直接回答：**

> 堆是完全二叉树，大顶堆父 ≥ 子，小顶堆父 ≤ 子。插入/删除 O(log n)，取堆顶 O(1)，建堆 O(n)。常用于优先队列、Top K、任务调度。

**追问 1：Top K 为什么用小顶堆？**

> 维护大小为 K 的小顶堆，堆顶是当前 K 个里最小的；新元素比堆顶大就替换，最终堆里就是最大的 K 个。

**追问 2：堆和 BST 的区别？**

> 堆只保证父子关系，不保证左右/整体有序；查找任意元素 O(n)，但取最值 O(1)。

**陷阱/加分：**

- JS 没有内置堆，需要自己实现或库。
- 建堆是 O(n)，不是 O(n log n)。

## Q5. BFS 和 DFS 的区别？怎么选？

**直接回答：**

> BFS 用队列，按层遍历，适合无权图最短路径、层序遍历；DFS 用栈/递归，适合连通性、拓扑排序、回溯。两者时间复杂度都是 O(V+E)。

**追问 1：BFS 为什么能找到最短路径？**

> 它按距离一层层扩展，第一次到达目标时的层数就是最短边数（无权图）。

**追问 2：DFS 递归太深怎么办？**

> 改迭代 + 显式栈，或增加递归限制/剪枝；JS 会栈溢出。

**陷阱/加分：**

- BFS 需要 visited，避免重复入队。
- DFS 也可以记录路径/回溯。

## Q6. 排序算法的复杂度和稳定性？

**直接回答：**

> 冒泡/选择/插入平均 O(n²)；归并/快排/堆排序平均 O(n log n)。归并稳定、O(n) 空间；快排不稳定、最坏 O(n²)、平均最快之一；堆排序不稳定、O(1) 空间。稳定指相等元素相对顺序不变。

**追问 1：快排最坏什么时候发生？**

> 已排序数组 + 固定 pivot（比如总选第一个/最后一个），每次划分极不平衡，退化成 O(n²)；随机 pivot/三数取中可缓解。

**追问 2：为什么归并排序适合链表？**

> 链表归并不需要随机访问，合并时只改指针，空间可以做到 O(1)（递归栈除外）。

**陷阱/加分：**

- JS 的 sort 默认按字符串排序。
- 稳定性对多字段排序很重要。

## Q7. 二分查找的前提和边界？

**直接回答：**

> 前提是数据有序（或具有单调性）。每次取中点，根据比较缩小一半，O(log n)。边界要统一：`left <= right` 配 `mid ± 1`，或者 `left < right` 配区间收缩，避免死循环。

**追问 1：`mid = (left + right) / 2` 有什么问题？**

> 大数相加可能溢出；用 `left + (right - left) / 2` 或位运算。

**追问 2：二分只能用于数组查找吗？**

> 不是，只要问题具有单调性，可以“二分答案”，比如最小化最大值、最大化最小值。

**陷阱/加分：**

- 循环条件、mid 取整、边界更新要配套。
- 找不到时返回 -1 还是插入位置，要明确。

## Q8. 动态规划的适用条件和解题步骤？

**直接回答：**

> 适用条件：重叠子问题、最优子结构。步骤：定义 dp[i] 含义、找状态转移方程、确定初始值、确定遍历顺序、必要时做空间优化。

**追问 1：DP 和贪心的区别？**

> 贪心每步取局部最优，不保证全局最优；DP 会保留子问题的最优解，能处理有重叠子问题的情况。

**追问 2：怎么判断能不能空间优化？**

> 如果 dp[i] 只依赖前几项，可以用滚动变量/一维数组；否则需要完整表。

**陷阱/加分：**

- 先写递归 + 记忆化，再改迭代，容易想清楚。
- 注意边界和初始值。

## Q9. 大 O 复杂度怎么分析？

**直接回答：**

> 看输入规模 n 增大时，时间/空间的增长趋势，忽略常数和低阶项。常见：O(1)、O(log n)、O(n)、O(n log n)、O(n²)、O(2ⁿ)。

**追问 1：O(n) 和 O(2n) 有区别吗？**

> 大 O 忽略常数，都是 O(n)；实际工程中常数可能很重要。

**追问 2：空间复杂度怎么算？**

> 额外使用的内存，不含输入本身；递归要算调用栈。

**陷阱/加分：**

- 最好/最坏/平均要区分。
- 摊还分析（如动态数组 push）也是常考点。

---

## Q10. LRU 怎么实现？

**直接回答：**

> 哈希表 + 双向链表。哈希表 O(1) 找到节点，双向链表维护最近使用顺序；访问/插入把节点移到头部，超出容量删除尾部。整体 O(1)。

**追问 1：为什么不用数组？**

> 数组移动元素 O(n)，无法 O(1) 调整顺序。

**追问 2：JS 里怎么用 Map 实现？**

> Map 保持插入顺序，get 后 delete + set 移到末尾，超出容量删除第一个 key。

**陷阱/加分：**

- LRU 是“最近最少使用”，不是“最久未使用”文字游戏。
- 并发场景要考虑锁。

---

## Q11. Top K 问题怎么做？

**直接回答：**

> 小顶堆维护 K 个元素，O(n log k)；或者快速选择（partition）平均 O(n)；数据量小也可以排序 O(n log n)。

**追问 1：为什么不是大顶堆？**

> 大顶堆堆顶是最大值，无法快速淘汰“当前 K 个里最小的”；小顶堆堆顶是 K 个里最小的，方便替换。

**追问 2：海量数据怎么办？**

> 分片 + 每片 Top K + 归并；或者用外部排序/分布式计算。

**陷阱/加分：**

- 频率统计先用哈希表。
- 注意内存限制。

---

## Q12. 进程和线程的区别？

**直接回答：**

> 进程有独立地址空间和资源，线程共享进程的代码/数据/堆，但有独立栈和寄存器。进程切换成本高，线程切换较低；进程崩溃通常不影响其他进程，线程崩溃可能影响整个进程。

**追问 1：线程共享什么？**

> 代码段、数据段、堆、打开的文件；栈、寄存器、程序计数器独立。

**追问 2：浏览器为什么多进程？**

> 隔离/安全/稳定，一个标签页崩溃不影响其他；渲染进程内还有主线程、合成线程、Worker 等。

**陷阱/加分：**

- JS 主线程单线程，但浏览器底层多线程。
- Web Worker 是线程级并行，不能操作 DOM。

## Q13. 死锁的条件和解决方法？

**直接回答：**

> 四个必要条件：互斥、持有并等待、不可剥夺、循环等待。解决：破坏任一条件，比如固定顺序加锁、超时释放、一次性申请所有资源、死锁检测与恢复。

**追问 1：为什么固定顺序加锁能避免死锁？**

> 所有线程按同一顺序申请资源，不会形成循环等待。

**追问 2：死锁和活锁的区别？**

> 死锁是互相等待、无法推进；活锁是一直重试但无法前进，状态不断变化。

**陷阱/加分：**

- 死锁不是“线程卡住”这么简单，要四个条件同时满足。
- 数据库/分布式锁也会死锁。

## Q14. 虚拟内存是什么？

**直接回答：**

> 每个进程看到独立的虚拟地址空间，由操作系统映射到物理内存。好处是隔离、安全、可以运行比物理内存更大的程序；通过页表、TLB、缺页中断管理。

**追问 1：缺页中断是什么？**

> 访问的页不在物理内存，操作系统从磁盘换入；如果内存满，按页面置换算法淘汰一页。

**追问 2：页面置换有哪些算法？**

> FIFO、LRU、Clock；LRU 命中率高但实现成本高，实际用近似 LRU。

**陷阱/加分：**

- 虚拟内存不是“硬盘当内存”这么简单，是地址映射 + 按需调页。
- 抖动（thrashing）是频繁换页导致性能下降。

---

## Q15. 栈和堆的区别？

**直接回答：**

> 栈由系统自动管理，存放局部变量/函数调用帧，速度快、空间小；堆存放对象/大块内存，由 GC 或手动管理，速度较慢、空间大。栈溢出通常是递归太深，堆泄漏通常是对象没释放。

**追问 1：JS 的原始值和对象分别在哪？**

> 原始值通常在栈/寄存器，对象在堆，变量保存引用；具体实现由引擎决定，面试按语义答。

**追问 2：为什么递归太深会栈溢出？**

> 每次调用都压一个栈帧，超过栈大小就溢出；可以改迭代或尾递归优化（JS 引擎支持有限）。

**陷阱/加分：**

- 栈和堆是内存区域，不是数据结构（虽然也有栈/堆结构）。
- 闭包变量通常在堆上。

---

## Q16. I/O 多路复用是什么？select/poll/epoll 的区别？

**直接回答：**

> 一个线程同时监听多个文件描述符，哪个就绪就处理哪个。select 有 fd 数量限制且线性扫描；poll 没数量限制但仍线性扫描；epoll 事件驱动，只返回就绪的 fd，适合大量连接（Linux）。

**追问 1：Node.js 为什么能高并发？**

> 它用 libuv 的事件循环 + I/O 多路复用（Linux epoll/macOS kqueue/Windows IOCP），单线程处理大量 I/O，不阻塞等待。

**追问 2：epoll 为什么快？**

> 内核维护就绪列表，不需要每次遍历所有 fd；适合大量连接、少量活跃的场景。

**陷阱/加分：**

- 多路复用不是“多线程”，是单线程管理多 I/O。
- CPU 密集任务仍会阻塞 Node 主线程。

---

## Q17. 用户态和内核态的区别？

**直接回答：**

> 用户态运行应用程序，权限受限；内核态运行操作系统内核，可以访问硬件。应用程序通过系统调用进入内核态，比如读文件、发网络包、创建线程。

**追问 1：为什么系统调用有开销？**

> 要切换特权级、保存/恢复上下文、参数拷贝，可能还有安全检查。

**追问 2：为什么要有用户态/内核态？**

> 隔离和安全，防止应用直接操作硬件/破坏系统。

**陷阱/加分：**

- 系统调用不是普通函数调用。
- 频繁系统调用会影响性能。

---

## Q18. TCP 和 UDP 的区别？

**直接回答：**

> TCP 面向连接、可靠、保证顺序，有流量/拥塞控制，速度较慢；UDP 无连接、不可靠、不保证顺序，但头部小、速度快。TCP 适合 HTTP/文件/聊天，UDP 适合视频/游戏/DNS/直播。

**追问 1：TCP 怎么保证可靠？**

> 序号 + ACK、超时重传、校验和、滑动窗口、拥塞控制。

**追问 2：UDP 能可靠吗？**

> 可以在应用层做确认/重传/排序，比如 QUIC；但那是应用层可靠性，不是 UDP 本身。

**陷阱/加分：**

- TCP 是字节流，不保留消息边界。
- UDP 保留数据报边界。

---

## Q19. TCP 三次握手和四次挥手？

**直接回答：**

> 三次握手：客户端 SYN，服务端 SYN+ACK，客户端 ACK；目的是双方确认收发能力并同步序列号。四次挥手：主动方 FIN，被动方 ACK，被动方 FIN，主动方 ACK；因为 TCP 全双工，两个方向要分别关闭。

**追问 1：为什么握手是三次不是两次？**

> 两次只能确认客户端能发/服务端能收，服务端无法确认客户端能收到自己的包；三次才能双向确认。

**追问 2：TIME_WAIT 有什么用？**

> 确保最后 ACK 到达、处理旧连接的迟到包；通常等 2MSL。

**陷阱/加分：**

- SYN 洪泛是常见攻击，用 SYN cookie 防御。
- 四次挥手不一定每次都是四次，有时 ACK/FIN 合并。

## Q20. HTTP/1.1、HTTP/2、HTTP/3 的区别？

**直接回答：**

> HTTP/1.1 是文本协议，持久连接但有队头阻塞，浏览器并发连接有限；HTTP/2 用二进制分帧、多路复用、头部压缩，解决 HTTP 队头阻塞，但仍有 TCP 队头阻塞；HTTP/3 基于 QUIC/UDP，解决 TCP 队头阻塞，支持 0-RTT 和连接迁移。

**追问 1：HTTP/2 的多路复用是什么？**

> 一个 TCP 连接上并行多个请求/响应流，不需要多个连接；流有 ID，帧可以交错。

**追问 2：HTTP/3 为什么用 UDP？**

> QUIC 在 UDP 上实现可靠传输、加密、多路复用，避免 TCP 的队头阻塞，握手更快。

**陷阱/加分：**

- HTTP/2 的 server push 实际使用很少。
- HTTPS 不等于 HTTP/2，但 HTTP/2 通常要求 TLS。

---

## Q21. HTTPS 的流程？

**直接回答：**

> HTTPS = HTTP + TLS。客户端和服务端协商 TLS 版本/套件，服务端返回证书，客户端验证证书（CA 签名、域名、有效期），双方用非对称加密/密钥交换协商对称密钥，之后用对称密钥加密通信。

**追问 1：为什么用混合加密？**

> 非对称加密安全但慢，适合交换密钥；对称加密快，适合传输数据。

**追问 2：证书的作用是什么？**

> 证明公钥属于这个域名，防止中间人攻击；证书由 CA 签名，客户端信任 CA。

**陷阱/加分：**

- HTTPS 不能防止服务器本身被黑。
- TLS 1.3 简化握手，支持 0-RTT/1-RTT。

---

## Q22. DNS 解析过程？

**直接回答：**

> 浏览器缓存 → 系统缓存 → hosts → 本地 DNS 服务器 → 根域名服务器 → 顶级域服务器 → 权威域名服务器；拿到 IP 后缓存并返回。

**追问 1：DNS 用 TCP 还是 UDP？**

> 通常 UDP 53，响应太大/区域传送用 TCP；DNS over HTTPS/TLS 也用 TCP/TLS。

**追问 2：怎么优化 DNS？**

> 缓存/TTL、`dns-prefetch`、`preconnect`、CDN 调度、HTTPDNS。

**陷阱/加分：**

- DNS 解析发生在 TCP 连接之前。
- CDN 会根据 DNS/Anycast 把用户调度到最近节点。

## Q23. 强缓存和协商缓存？

**直接回答：**

> 强缓存看 `Cache-Control/Expires`，命中不发请求，直接用本地副本；协商缓存看 `ETag/Last-Modified`，发请求带 `If-None-Match/If-Modified-Since`，未修改返回 304，不传 body。

**追问 1：为什么 HTML 不长期缓存？**

> HTML 引用的 JS/CSS hash 会变，HTML 缓存会导致用户拿不到新资源；通常 `no-cache` 每次校验。

**追问 2：`no-cache` 和 `no-store` 的区别？**

> `no-cache` 可以缓存但每次要校验；`no-store` 完全不缓存。

**陷阱/加分：**

- 带 hash 的静态资源可以长缓存 + immutable。
- 缓存要配合版本号和 CDN 刷新。

---

## Q24. 跨域怎么解决？CORS 预检是什么？

**直接回答：**

> 开发用代理，生产用 CORS/同域/Nginx 反向代理；JSONP 只支持 GET，已少用。CORS 预检是浏览器对非简单请求先发 OPTIONS，服务端返回允许的 origin/method/header，浏览器再发真实请求。

**追问 1：为什么有预检？**

> 防止跨域请求对服务器产生副作用；浏览器先确认服务器是否允许。

**追问 2：带 cookie 的跨域要注意什么？**

> `credentials: 'include'`，服务端 `Allow-Credentials: true`，`Allow-Origin` 不能是 `*`。

**陷阱/加分：**

- CORS 是浏览器行为，服务端/curl 不受限。
- 代理是开发方案，生产要配网关。

---

## Q25. 事务的 ACID 和隔离级别？

**直接回答：**

> ACID：原子性、一致性、隔离性、持久性。隔离级别：读未提交、读已提交、可重复读、串行化；级别越高，并发问题越少但性能越低。MySQL InnoDB 默认可重复读。

**追问 1：脏读、不可重复读、幻读的区别？**

> 脏读读到未提交数据；不可重复读同一事务两次读同一行结果不同；幻读同一事务两次范围查询行数不同。

**追问 2：可重复读怎么实现？**

> InnoDB 用 MVCC + 间隙锁/next-key lock，读快照，基本解决幻读。

**陷阱/加分：**

- 隔离级别和锁不是一回事，MVCC 也能提供隔离。
- 分布式事务更复杂（2PC/TCC/Saga）。

## Q26. 索引的原理？最左前缀是什么？

**直接回答：**

> 索引像书的目录，常见结构是 B+ 树；叶子节点存数据/主键，非叶子只存键，高度低、范围查询快。联合索引按定义顺序匹配，叫最左前缀；跳过最左列通常用不到索引。

**追问 1：聚簇索引和二级索引的区别？**

> 聚簇索引叶子存整行数据；二级索引叶子存主键，查询其他字段可能要回表。

**追问 2：索引失效的常见情况？**

> 对索引列做函数/运算、隐式类型转换、`LIKE '%x'` 前导模糊、OR 两边没都走索引、不符合最左前缀。

**陷阱/加分：**

- 索引加速读，但降低写速度、占空间。
- 覆盖索引可以避免回表。

## Q27. SQL 注入怎么防？

**直接回答：**

> 用参数化查询/预编译，不要拼接 SQL；用 ORM；输入校验；最小权限；错误信息不要泄露数据库细节。

**追问 1：为什么参数化查询能防注入？**

> SQL 结构和参数分开，参数只作为值，不会被解析成 SQL 语句。

**追问 2：ORM 就一定安全吗？**

> 不一定，ORM 的 raw SQL/字符串拼接仍可能注入；要看具体用法。

**陷阱/加分：**

- 前端校验不能替代后端参数化。
- 日志里不要打印敏感 SQL/密码。

## Q28. 范式、NoSQL、Redis 了解吗？

**直接回答：**

> 范式减少冗余：1NF 字段原子、2NF 消除部分依赖、3NF 消除传递依赖；实际会适当反范式换性能。NoSQL 有 Redis（KV/缓存）、MongoDB（文档）、ES（搜索）等。Redis 常用作缓存、分布式锁、排行榜。

**追问 1：缓存穿透/击穿/雪崩？**

> 穿透：查不存在的数据，缓存空值/布隆过滤器；击穿：热点 key 过期，互斥锁/永不过期；雪崩：大量 key 同时过期，随机过期/熔断/多级缓存。

**追问 2：Redis 分布式锁怎么实现？**

> `SET key value NX EX` 加锁，Lua 脚本校验 value 后删除；要考虑锁过期/续期/误删。

**陷阱/加分：**

- 缓存和数据库一致性要按业务选策略。
- 不要用 Redis 存所有数据。

## Q29. XSS 和 CSRF 的区别？怎么防？

**直接回答：**

> XSS 是把恶意脚本注入页面执行，分存储/反射/DOM 型；防御是转义、textContent、CSP、HttpOnly。CSRF 是诱导已登录用户向目标站点发请求；防御是 CSRF Token、SameSite Cookie、校验 Origin/Referer、关键操作二次验证。

**追问 1：XSS 和 CSRF 能互相替代吗？**

> 不能。XSS 是脚本执行，CSRF 是借用用户登录态发请求；XSS 可以绕过 CSRF Token，所以 XSS 更危险。

**追问 2：JWT 放 localStorage 有什么风险？**

> XSS 能读 localStorage 偷 token；放 HttpOnly Cookie 可以降低 XSS 读取风险，但要防 CSRF。

**陷阱/加分：**

- CSP 是纵深防御，不是万能。
- 富文本要白名单清洗。

## Q30. 常见设计模式有哪些？前端用在哪？

**直接回答：**

> 单例（全局 store/请求实例）、工厂（组件/对象创建）、观察者/发布订阅（事件总线/响应式）、策略（表单校验/支付方式）、装饰器（HOC/埋点）、适配器（接口数据归一化）、代理（Vue3 响应式/HTTP 代理）。

**追问 1：观察者和发布订阅的区别？**

> 观察者：主题直接维护观察者列表；发布订阅：通过事件中心解耦发布者和订阅者。

**追问 2：策略模式在表单里怎么用？**

> 把每种校验规则封装成函数/对象，按字段类型选择，避免大段 if/else。

**陷阱/加分：**

- 设计模式不是越多越好，解决实际问题才用。
- 前端框架本身大量使用这些模式。

## Q31. MVC、MVVM、SOLID 是什么？

**直接回答：**

> MVC 是 Model-View-Controller，Controller 处理输入；MVVM 是 Model-View-ViewModel，双向绑定，Vue 常被这样描述；React 通常只负责 View，状态/路由/请求是另外的层。SOLID 是单一职责、开闭、里氏替换、接口隔离、依赖倒置。

**追问 1：React 是 MVC 吗？**

> React 本身更接近 View 层，配合状态管理/路由/请求形成完整架构；不是严格 MVC。

**追问 2：单一职责和组件拆分什么关系？**

> 一个组件只做一件事，拆小后更容易复用/测试；但不要拆得过碎。

**陷阱/加分：**

- 架构模式不是框架标签，要看实际数据流。
- SOLID 是指导思想，不是硬规则。

## Q32. JWT 和密码存储怎么保证安全？

**直接回答：**

> JWT 是 header.payload.signature，payload 只是 Base64 编码，不是加密，不能放密码/密钥；签名防篡改，不防泄露。密码用 bcrypt/argon2/scrypt + 随机盐存储，不要明文/MD5/SHA1；传输用 HTTPS。

**追问 1：JWT 怎么过期/刷新？**

> 设置短过期 + refresh token；刷新 token 存服务端/HttpOnly Cookie，支持撤销。

**追问 2：为什么不能用 MD5 存密码？**

> MD5 太快、可彩虹表/暴力破解；要用慢哈希 + 盐。

**陷阱/加分：**

- JWT 无法主动失效（除非黑名单/短过期）。
- 敏感操作要二次验证。
